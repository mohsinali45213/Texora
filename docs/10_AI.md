# 10 — AI Assistant

## Purpose

Provide a buyer-facing conversational and search-augmenting layer on top of real marketplace data, using the **Hugging Face Inference API**. The AI never invents products or facts — it is always grounded in data fetched from MongoDB at request time.

## Architecture

```
Buyer input (text or voice-transcribed text)
        │
        ▼
app/api/ai/*/route.ts   (thin controller, auth + validation)
        │
        ▼
services/ai.service.ts  (orchestration)
        │
        ├── ai/context-builder.ts   → repositories/product.repository.ts (fetch relevant products)
        │
        ├── ai/prompts/*.prompt.ts  → build final prompt string
        │
        ▼
lib/huggingface.ts       (calls Hugging Face Inference API)
        │
        ▼
Response parsed → returned to client
```

All AI logic is isolated in `ai/` and `services/ai.service.ts`. Route handlers and UI components never call Hugging Face directly.

## Knowledge Source

The only knowledge source is the `products` collection (plus, where relevant, the requesting buyer's `buyerProfile` for personalization). `context-builder.ts` performs a scoped MongoDB query — text search, category match, or "same category as reference product" — to gather a small candidate set (e.g., top 10–20 products) that is serialized into the prompt as structured context. No vector database or embedding store is used; this is a deliberate simplification for the hackathon timeframe.

## Prompt Flow

1. **Build context**: fetch a relevant, bounded set of products from MongoDB based on the request type (see per-feature flows below).
2. **Build prompt**: combine a fixed system instruction ("You are a marketplace assistant for a B2B textile platform. Only reference products from the provided list. Do not invent products, prices, or stock.") with the serialized product context and the user's message/query.
3. **Call Hugging Face Inference API** via `lib/huggingface.ts` with the assembled prompt.
4. **Parse response**: for structured outputs (search filters, comparisons), the prompt instructs the model to return strict JSON, which is parsed and validated before being sent to the client; on parse failure, fall back to a safe default (e.g., empty filter / plain text passthrough).
5. **Return** to the client: natural language reply and/or a list of referenced product IDs resolved back to full product documents from the database (never trusting product details generated by the model itself).

## Feature-Specific Logic

### Conversational Chat (`/api/ai/chat`)
- Maintains a short conversation history (client-sent, capped at last N turns) for context continuity.
- Context builder does a lightweight keyword extraction from the latest message to pull relevant products.
- Response includes `reply` (text) and optional `referencedProducts` resolved from the DB.

### Natural Language Search (`/api/ai/search`)
- Prompt instructs the model to convert free text (e.g., "cotton fabric under ₹500 for shirts") into a strict JSON filter object matching the existing filter schema (`category`, `fabricType`, `minPrice`, `maxPrice`, `keywords`).
- The parsed filter is then run through the normal `product.repository.ts` query — the model never queries the DB itself, it only produces filter parameters.

### Fabric Recommendations (`/api/ai/recommend`)
- Context = buyer's `buyerProfile` (preferred fabrics, categories, budget) + a candidate product set matching those preferences.
- Model ranks/selects a shortlist from the candidate set only (never products outside it) and returns product IDs with a one-line reason each.

### Product Comparison (`/api/ai/compare`)
- Input: 2–3 product IDs.
- Context = full documents for exactly those products.
- Model produces a natural-language comparison summary (materials, price, stock, use case) strictly from the provided attributes.

### Similar Product Suggestions (`/api/ai/similar`)
- Context = the reference product + a candidate set from the same/related category.
- Model (or a simple similarity heuristic as a fallback) ranks the top 4–6 most similar candidates by category/fabric/price proximity, optionally refined with an LLM re-rank.

### Product Q&A (`/api/ai/qa`)
- Context = the single product's full document (description, specs, stock, price, colors).
- Model answers strictly from that document; if the question can't be answered from available fields, it responds that the information isn't available rather than guessing.

## Voice-Based Assistance

Voice input is handled entirely client-side (browser Web Speech API or a lightweight recorder + transcription call) to produce text, which is then sent through the same `/api/ai/chat` endpoint as a normal message. There is no separate voice-specific backend logic — this keeps the AI layer single-pathed and easy to reason about.

## Limitations (By Design, Not Bugs)

- No persistent AI memory across sessions — each request builds fresh context from the current DB state and the client-supplied recent conversation history only.
- No vector search / semantic embeddings — candidate retrieval uses straightforward MongoDB queries (text index, category match), which is sufficient at hackathon data scale.
- No autonomous actions — the AI cannot add items to cart, place orders, or modify inventory; it can only inform and suggest.
- No multi-agent orchestration — a single prompt/response call per feature, no agent loops or tool-chaining.
- Recommendation and similarity ranking quality is bounded by the small candidate sets pulled from MongoDB; this is acceptable for demo purposes.
